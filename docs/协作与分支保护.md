# 协作与分支保护

这份文档说明：当仓库不止一个人写时，靠什么防止一次错误改动毁掉项目。

先给结论：**仓库里能做的自动化只能挡住「明显错误」**（提交了数据文件、泄了 token、测试挂了、改坏了冻结证据）；真正危险的是「看完回测结果回头改阈值」这类流程问题，只能靠分支保护 + 必须 review + 预注册纪律。三层要一起上，缺一层就有洞。

---

## 一、现状

| 层 | 已经有的 | 还缺（需要你在 GitHub 网页点几下） |
|---|---|---|
| 仓库设置 | 公开仓库，main 分支 | 分支保护规则（ruleset）、标签保护、fork PR 需审批 |
| 仓库自动化 | `scripts/repo_guard.py`、`.github/workflows/ci.yml`、`.github/CODEOWNERS`、PR 模板、210 项离线测试 | 第一次 push 后确认 CI 真的跑起来 |
| 流程 | `CONTRIBUTING.md`、三份策略报告 + `registry.json`、各阶段预注册文档 | 自己也要遵守「不直接推 main」 |

## 二、第一层：GitHub 仓库设置（必须手动点，约 5 分钟）

这些设置不在代码里，必须用有 admin 权限的账号在网页上开。**不开的话，协作者可以直接 `git push origin main`，前面所有 CI 都白做**（CI 只是 advisory，不拦住合并）。

### 2.1 main 分支保护（Rulesets）

路径：仓库 → **Settings → Rules → Rulesets → New branch ruleset**

建议填法：

- **Ruleset Name**: `protect-main`
- **Enforcement status**: `Active`
- **Target branches**: `Add target → Include by pattern → main`
- 勾选项：
  - ✅ **Restrict deletions**（不许删 main）
  - ✅ **Block force pushes**（不许强推覆盖历史）
  - ✅ **Require a pull request before merging**
    - Required approvals: `1`
    - ✅ Dismiss stale pull request approvals when new commits are pushed
    - ✅ Require review from Code Owners
    - ✅ Require conversation resolution before merging
  - ✅ **Require status checks to pass**
    - 添加两个检查：`仓库纪律`、`离线测试 py3.12`（名字来自 `.github/workflows/ci.yml` 里的 job `name`）
    - ✅ Require branches to be up to date before merging
  - （可选）Require linear history
  - （可选）Require signed commits
- **Bypass list**：只留你自己（`Repository admin`）。给协作者写权限时，不要把他们加进 bypass。

⚠️ 开了这条之后，你自己也要走「建分支 → 开 PR → 等 CI → 合并」，直接 `git push origin main` 会被拒。这是设计意图，不是故障。

### 2.2 标签保护

路径：**Settings → Rules → Rulesets → New tag ruleset**

- **Target tags**: `Include by pattern → v*`
- ✅ Restrict deletions、✅ Block force pushes
- 效果：`v1.0-growth-cap25-20261022` 这类冻结标签不能被删、不能被移动。

### 2.3 fork PR 的 CI 需要审批

路径：**Settings → Actions → General → Fork pull request workflows**

- 选 **Require approval for all external contributors**

原因：公开仓库任何人都能提 PR，而 PR 里的 workflow 会用到仓库的 Actions 额度。默认只对首次贡献者要审批，改成「所有人」更省心。

### 2.4 关掉不需要的写入口

- **Settings → General → Danger Zone**：保持仓库公开，但确认没有多余的协作者。
- 需要多人协作时，用 **Settings → Collaborators** 加人，权限给 `Write`（不要给 `Admin`），配合 2.1 的 PR 要求，他们只能通过 PR 改东西。

## 三、第二层：仓库内自动化（已提交）

### 3.1 `scripts/repo_guard.py` —— 仓库纪律

CI 的第一个 job，本地也能跑：

```bash
python scripts/repo_guard.py
```

检查 6 类问题：

| 检查 | 挡住的典型事故 |
|---|---|
| 单文件 > 5 MB | 误把 parquet / 数据库 / 结果集提交进 git |
| 禁止的扩展名 | `.parquet` `.feather` `.h5` `.pkl` `.npy` `.db` `.zip`；`.csv/.gz` 只准放 `results/releases/` |
| 凭据扫描 | `ghp_…`、`github_pat_…`、`sk-…`、`AKIA…`、私钥、URL 里带账号密码、硬编码 password |
| 冻结证据 | `results/releases/*/manifest.csv` 里每个文件的 sha256 必须对得上（改一个字节就红） |
| 策略台账 | `docs/策略报告/registry.json` 能解析、`report` 指向的文件存在、status 合法 |
| 忽略规则 | `_tmp/`、`data/cache/`、`results/` 确实被忽略；`results/releases/` 确实不被忽略 |

### 3.2 `.github/workflows/ci.yml` —— 测试

两个 job：

- **仓库纪律**：跑 `repo_guard.py`
- **离线测试 py3.12**：`tests/run_all.py --list` 里标 `offline` 的 12 个套件，每个套件**单独起一个进程**跑

为什么单独起进程：18 个套件在一个进程里跑时，`插件/CLI` 套件会污染全局状态，导致后面 `多因子` 套件的 `fmcap_q05` 全变 NaN——那是测试之间的串扰，不是产品 bug。分进程跑既隔离了状态，也让失败定位到具体套件。

**CI 会跳过 5 个套件**（`python tests/run_all.py --list` 里标 `lake` 的）：`factors`、`refdata`、`events`、`holdout`、`web_source`。它们要读 `D:/quant-data` 的真实数据湖或外网，云端 runner 上没有。**发版前必须在本机跑一次全量**：

```bash
python tests/run_all.py
```

现在本机全量是 210 项，唯一已知失败见 `docs/策略报告/README.md` 的说明。

### 3.3 `.github/CODEOWNERS`

`* @1174659240`：所有路径默认归你 review。配合 2.1 的「Require review from Code Owners」，协作者的 PR 必须你点过才能合并。

### 3.4 PR 模板

`.github/pull_request_template.md`，强制作者回答四件事：改了什么、影响范围（含「是否改冻结口径」）、自查清单、与冻结结论的关系。

## 四、第三层：流程（自动化管不了的部分）

CI 能证明「代码能跑、测试没挂、没提交脏文件」，**不能证明「这个改动是对的」**。以下几条只能靠人和文档：

1. **改数值结果必须附新旧对比**，并在 PR 里登记试验次数（DSR 的 N 只增不减）。
2. **冻结口径（因子集、权重、阈值、风控规则）的改动必须先写预注册文档**，再改代码。事后补文档 = 无效。
3. **样本外只能消费一次**：已消费的 holdout 不能再用来看效果、挑参数。谁在 PR 里动了 `results/growth/holdout/` 的结论，视为污染。
4. **旧结论要被取代时，必须在 `registry.json` 与报告里标 `superseded`**，不能悄悄改数字。
5. **改 `scripts/` 里冻结策略的入口**（`growth_backtest.py` 的 `SPECS`、`growth_risk.py` 的常量、`risk_system.py` 的 `EXT_*`），等于改了策略定义，必须重跑并更新报告。

---

## 五、可选：本地 pre-push 钩子

不想每次都等 CI，可以装一个本地钩子，push 前自动跑仓库自检：

```bash
git config core.hooksPath .githooks
```

`.githooks/pre-push` 只跑 `repo_guard.py`（1 秒内），不跑测试——测试太慢，留给 CI。

## 六、我需要你确认的事

1. 上面 2.1–2.4 的网页设置，你自己点，还是我给你一个设备授权码（需要再授权一次，含 `repo` 权限）让我用 API 建 ruleset？
2. 是否要开「Require linear history」和「Require signed commits」？前者让历史更干净（只能 squash/rebase 合并），后者要求每台机器配 GPG/SSH 签名，配置成本高。
3. 协作者打算给谁、给什么权限？如果暂时只有你一个人，**2.1 仍然值得开**——它防的是「未来的自己手滑 `git push -f`」。
