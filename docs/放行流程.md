# 策略放行流程

这份文档回答三个问题：一条策略要经过哪些检查才能算「可发布」，每关由谁执行、看什么数字，以及 holdout 数据怎么保证协作者根本拿不到。

一句话版本：**关卡 1 每次提交都跑；关卡 2 在申请毕业时手动跑，分「硬否决 + 强参考」两层，硬否决不过就不许碰 holdout；关卡 3 由机器执行一次、判据写死、跑完就作废。**

---

## 一、三级放行

| 关卡 | 何时跑 | 谁执行 | 看什么 | 不通过会怎样 |
|---|---|---|---|---|
| 关卡 1 日常 CI | 每次 push / PR | GitHub Actions | `repo_guard` 仓库纪律 + 12 个离线测试套件 | PR 红，不能合并 |
| 关卡 2 稳健性门禁 | 申请毕业时手动跑一次 | 提交者本人 | 硬否决 4 项（泄露、置换、成本、容量）+ 强参考 8 项 | 硬否决不过 → **禁止进入关卡 3**；强参考多重告警 → 关卡 3 只判 HOLD |
| 关卡 3 样本外验收 | 只跑一次，跑完作废 | 机器（`scripts/gate_holdout.py`） | 年化 ≥ 样本内同类行情的 25% 分位、夏普 ≥ 同类行情 25% 分位、年化超额 > −5pp | 结论 FAIL，写进台账，不能自己再跑一遍 |

三条纪律：

1. **关卡 2 的硬否决层是闸门，强参考层是体检。** 硬否决不过，`gate_holdout.py` 直接非 0 退出、拒绝消费 holdout；强参考≥2 项不达标或有严重不足时，即使关卡 3 行情达标也只判 `HOLD`，要所有者用 `--owner-confirm "理由"` 才放行。
2. **holdout 只消费一次。** `scripts/gate_holdout.py` 跑完会写 `results/gates/holdout-consumed.json`，之后任何再跑都要 `--force`，而 `--force` 的出现本身就是要解释的事。
3. **判据改动 = 协议改动。** 关卡 2 的 `criteria_sha` 与关卡 3 的 `criteria_sha` 都会写进结论文件；改了判据，sha 就变，任何人对比历次结论都能看出来。

---

## 二、关卡 1：日常 CI

`.github/workflows/ci.yml` 两个作业：

- **仓库纪律**：跑 `scripts/repo_guard.py`。检查跟踪文件数、单文件体积、禁止入库的数据/结果、凭据扫描、冻结归档 sha256、`registry.json` 台账、`.gitignore` 规则、文本卫生（控制字符）、**holdout 隔离**（见 §四）。
- **离线测试 py3.12**：12 个离线套件逐套件独立进程跑，`--skip-lake`，不碰数据湖。

本地等价命令：

```bash
python -X utf8 tests/run_all.py --skip-lake
python -X utf8 scripts/repo_guard.py
```

## 三、关卡 2：稳健性门禁（硬否决 + 强参考）

```bash
# 首次预注册：锁定策略类型与目标规模（必须先做，否则后面直接拒绝）
python -X utf8 -m scripts.gate_robustness --declare --strategy growth_cap25 \
    --archetype small_cap_fast --target-aum 50000000 --note "小盘成长 v1.0"

python -X utf8 -m scripts.gate_robustness              # 完整两层检查，约 15 分钟
python -X utf8 -m scripts.gate_robustness --light      # 只跑轻量项，不产判决（开发用）
```

输出 `results/gates/gate2-<策略>-<时间戳>.json` 与同名 `.md`，结论四选一：
`CLEAR`（可进关卡 3）/ `MULTI-ALARM`（多重告警，需所有者确认）/ `HARD-FAIL`（硬否决不过）/ `LIGHT`（轻量，不产判决）。

### 3.1 硬否决层（任何一项不过 → 禁止进入关卡 3、禁止消费 holdout）

| 检查 | 判定线 | 为什么是这条线 |
|---|---|---|
| `gate1_offline` | 离线测试全过 | 无未来函数 / 数据泄露的回归检查都在离线套件里 |
| `perm_p` | 置换检验 p ≤ 0.05 | 信号不是随机选股选出来的 |
| `cost_tier_cagr` | 该策略类型成本档下年化 > 0 | 成本吃掉全部收益的策略没有放行意义 |
| `capacity_p95` | 目标规模下单票日参与率 p95 ≤ 10% | 卖得掉；按预注册声明的规模算，不按拍脑袋的规模算 |
`gate_holdout.py` 启动时先校验这一层（`gate2_precheck`）：报告必须是 `gate2-v2`、判据 sha 未变、预注册仍与锁文件一致、硬否决全过。任何一条不满足，直接退出码 3，连关卡 1 都不跑。

口径备注：

- `capacity_p95` 用**持仓市值 / 20 日均成交额**做保守估计（实际下单量约为持仓的 1/60，因为年换手 3~5 倍），全样本全部 (日, 票) 取 p95；权重文件是稠密矩阵、未持仓写 0，计算前先剔零。
- `state_share` 用**日超额（策略 − 同池等权基准）**而不是裸收益：纯多头策略在上涨日的裸收益天然占大头，用裸收益算会把每个多头策略都判成 1.0，指标没有分辨力。E 层整段未触发时（一侧 0 天）该维度不参与计算，避免凭空多出一个「严重告警」。

### 3.2 策略类型分档（预注册时锁定，禁止看结果再选档）

| 档位 | 适用 | 成本档 | 说明 |
|---|---|---|---|
| `small_cap_fast` | 小盘高换手型 | 30bp 往返 | 持仓偏小、年换手 3~5 倍、容量小；放宽到 30bp，不要求 50bp |
| `large_cap_slow` | 大盘低换手型 | 50bp 往返 | 大市值、低换手、容量大；按 50bp 检验 |

档位与目标规模写在 `results/gates/prereg/<策略>.json`，并由 `results/gates/prereg-lock.json` 记 sha。想改必须 `--relock --reason "..."`，旧档进 `history`，看得到改过什么、为什么改。

### 3.3 强参考层（不自动否决，但必须完整写进报告）

DSR、PBO、bootstrap 夏普下限、IS/OOS 年化比、参数扰动夏普极差、参数扰动年化极差、WFA 正年占比、单一行情状态超额集中度，共 8 项。判定线与「严重不足」线（比判定线更宽）都写死在脚本的 `SOFT` / `SEVERE` 里。

- 不达标 ≥ 2 项，或有任何一项落到「严重不足」→ 结论标 **多重稳健性告警**。
- 多重告警时，即使关卡 3 行情达标，`gate_holdout.py` 也只判 `HOLD`；所有者要放行必须显式 `--owner-confirm "看过强参考层，理由…"`，理由会写进结论文件的 `owner_confirmation` 字段。

**为什么不全塞进硬否决**：DSR 要按试验次数打折、PBO 对参数邻域敏感、WFA 受窗口长度限制，这几项天然对小盘高换手策略不利。把它们全部变成硬门禁，等于用大盘低换手策略的尺子量小盘策略，会把有真实信号但样本短的策略直接判死。所以把「能证明造假/卖不掉」的四项做成硬闸门，把「稳健性够不够厚」的八项做成告警 + 人工确认。

## 四、holdout 数据隔离

holdout（2025-01-01 起）是**所有者的一次性验收集**。协作者不应该持有，也不应该能通过复现流程拿到。

| 入口 | 默认行为 | 打开方式 |
|---|---|---|
| `scripts/reproduce_lake.py` | `split` / holdout 的 `parquet`、`valuation` 阶段**默认跳过**；所有采集命令显式带 `--end 2024-12-31` | `--allow-holdout` **且** 环境变量 `QUANT_OWNER=1` |
| `scripts/data_pack.py` | `core` / `all` 预设都不含 `holdout` 层 | `--with-holdout` 且 `QUANT_OWNER=1` |
| `scripts/data_pull.py` | `core` 预设不含 `holdout` 层 | `--with-holdout` 且 `QUANT_OWNER=1` |
| `scripts/repo_guard.py` | 扫描公开脚本里是否出现 holdout 路径拼接 | 不允许「为了跑通」加例外 |
| `quant/lake.py` | 读 holdout 层需要 `allow_holdout=True`，否则 `PermissionError` | 显式传参 |

`QUANT_OWNER` 是**流程隔离，不是密码学隔离**：它防的是「协作者照着文档跑一遍，顺手把 holdout 也建出来」，防不了有人改代码。真要防，得靠分支保护（`.github/CODEOWNERS` + 必须 review）。

协作者拿到手的数据湖，最新日期应该是 **2024-12-31**。自查：

```bash
python -X utf8 -m scripts.reproduce_lake --audit-cutoff
```

> 所有者本机例外：本机早年的手工采集把 2025+ 数据写进了 `raw` / `valuation` / `fundamentals` / `events` / `delisted`，所以在这一台上跑 `--audit-cutoff` 会报越界。这个检查是给**全新复现出来的湖**用的。

## 五、关卡 3：一次性样本外验收

```bash
python -X utf8 -m scripts.gate_holdout            # 正式验收（会消费 holdout）
python -X utf8 -m scripts.gate_holdout --dry-run  # 只做关卡 2 校验 + 关卡 1，不动 holdout
```

执行顺序：

1. **关卡 2 前置校验**：读最新 `gate2-*.json`，确认新版、判据 sha 未变、预注册与锁文件一致、硬否决层全过。
   任何一条不满足 → 退出码 3，**连关卡 1 都不跑，更不碰 holdout**；
2. 关卡 1：本地跑 `tests/run_all.py --skip-lake`，退出码记进结论；
3. 若 `results/gates/holdout-consumed.json` 已存在则拒绝（退出码 2）；
4. 用冻结姿态跑 `scripts/growth_holdout.py`（输出到 `results/gates/holdout-<时间戳>/`）；
5. 按下面四步算底线并判决；
6. 写 `results/gates/holdout-verdict.json`，并落 `holdout-consumed.json`。

判决只有三种：`PASS`、`FAIL`、`HOLD`。`HOLD` 出现在「行情与关卡 1 都达标，但关卡 2 报了多重稳健性告警」时，此时要所有者显式确认：

```bash
python -X utf8 -m scripts.gate_holdout --owner-confirm "看过强参考层：PBO 高但样本短，接受"
```

理由会写进结论文件的 `owner_confirmation` 字段；没有这个字段的 PASS 才算是自动放行。

```bash
# 用当前判据重算一份已消费的 holdout（只读，不覆盖一次性标记，结论标为「重算、非盲测」）
python -X utf8 -m scripts.gate_holdout --evaluate-existing results/growth/holdout
```

### 判据 v3：先认行情，再拿样本内同类行情的下分位当底线

1. **认行情**：用同池等权基准算这一段窗口的年化、波动、最大回撤，打一个标签
   （趋势：上涨 ≥ +10% / 下跌 ≤ −10% / 其余震荡；形态：高波动或深回撤 ≥ 30% 或回撤 ≤ −30% / 低波动 ≤ 18% / 其余中等）。
2. **回样本内找同类**：把 2017-01~2024-12 的样本内切成与 holdout **等长**的滚动窗口（步长 5 个交易日），
   对每个窗口用同一套规则打标签，只留标签相同的窗口。
3. **定底线**：取同类窗口里策略年化的 **25% 分位**、夏普的 **25% 分位**。
   同类窗口少于 4 个时退化为全样本分位，并在结论里注明 `floor_fallback = true`。
4. **判决**：holdout 的年化 ≥ 年化底线、夏普 ≥ 夏普底线，且相对同池等权年化不落后超过 5pp。

| 判据 | 阈值 | 理由 |
|---|---|---|
| 年化 | ≥ 同类行情窗口的 25% 分位 | 同类行情下，策略本来就该有这么多；跌破说明策略在新样本里失效了 |
| 夏普 | ≥ 同类行情窗口的 25% 分位 | 光看收益会被行情本身带偏，风险调整后才可比 |
| 年化超额（vs 同池等权） | > −5pp | 兜底：底线很低时，也不能被「同池随便买」甩开 |

为什么不用「样本外 / 样本内保留率」：样本内 8 年的 9.5% 里混着四种完全不同的行情，
拿一个全样本均值当分母，等于要求新样本复制「历史上所有行情的平均」，这既不可比也不可达。
为什么不用「日频超额 t ≥ 2」：1.8 年的样本外，日频超额 t 的标准误太大，实测只有 0.7；
把它当硬门槛等于预先判死，与「用底线判断是否掉太多」的初衷不符。

判据版本号写在 `CRITERIA_VERSION`（当前 `v3`），`criteria_sha` 是判据字典的 sha256 前 16 位，
每次判决都记进结论文件，便于日后核对「当时用的是哪套标准」。

## 六、留痕

| 文件 | 内容 |
|---|---|
| `results/gates/prereg/<策略>.json` | 关卡 2 预注册：策略类型档位、目标规模、声明时间 |
| `results/gates/prereg-lock.json` | 预注册锁（sha + 改档 history，改一次记一次） |
| `results/gates/gate2-*.json` / `.md` | 关卡 2 每次的结果（可多份，取最新；判据 sha 变了旧报告自动失效） |
| `results/gates/holdout-verdict.json` | 关卡 3 结论（全项目一份，覆盖写；含 `verdict` / `blocked_by` / `owner_confirmation`） |
| `results/gates/holdout-verdict-recheck.json` | 用新判据重算旧结论的结果（标明「非盲测」） |
| `results/gates/holdout-consumed.json` | holdout 已消费的标记（含 commit、判据 sha、结论） |
| `docs/策略报告/registry.json` | 策略台账（含 `release`、`superseded` 关系） |
| `results/growth/robustness/trial-ledger.json` | 试验次数账本（DSR 的 N 从这里来） |

## 七、改判据 / 改流程的顺序

1. 先在 `docs/放行流程.md` 写清楚「为什么改」，并给出旧判据下会发生什么；
2. 再改脚本里的判据常量（关卡 3 是 `CRITERIA`；关卡 2 是 `HARD` / `SOFT` / `SEVERE` / `ARCHETYPES`）；
3. 跑 `tests/run_all.py gates` 确认纯函数测试仍过；
4. 提交时在 PR 描述里贴新旧 `criteria_sha` 与理由；
5. 已消费过的 holdout **不因判据改动而恢复**；关卡 2 判据一变，旧报告自动失效（前置校验会拒绝）。
