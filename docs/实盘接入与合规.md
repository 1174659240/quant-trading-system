| 磁盘/内存 | C: 可用 52.9GB；内存检测项因 `wmic` 不可用而跳过 |

**结论：可以做日线低频多因子的选股 + 半自动下单（人肉过一道手），还不具备全自动下单条件。**

## 1. 三条通道，能力与前置条件

| 通道 | 名字 | 是否需要券商开通 | 是否需要本机客户端 | 能否自动下单 | 本机状态 |
| --- | --- | --- | --- | --- | --- |
| 半自动（订单文件） | `csv` | 不需要（你手工在券商 App 下单） | 不需要 | ❌ 人肉确认 | ✅ 当前默认 |
| 本地模拟 | `paper` | 不需要 | 不需要 | 只是本地账本 | ✅ 可用 |
| 迅投 QMT | `qmt` | **需要**（程序化交易权限 + 客户端） | **需要**（MiniQMT 常驻） | ✅ | ⛔ 前置条件不满足 |

切换只需改 `config.toml`：

```toml
[gateway]
name = "csv"        # csv（半自动，默认） / paper（本地模拟） / qmt（自动）
dry_run = true      # true＝只出 <日期>-orders.preview.csv，永不下单
```

代码位置：`quant/gateway/base.py`（通道接口）、`csv_gateway.py`、`paper_gateway.py`、`qmt_gateway.py`；
工厂与配置：`quant/gateway/config.py` 的 `build_gateway()` / `load_gateway_config()`。

## 2. 成熟券商/机构的下单流程，与本工程的对应

机构的交易链路（简化）：**信号 → 组合构建 → 订单生成 → 事前风控 → 报盘 → 成交回报 → 持仓/资金 → 日终对账与清算**，
每一环都要能留痕、能复现、能急停。逐条对应：

| 机构做法 | 为什么这么做 | 本工程实现 |
| --- | --- | --- |
| 信号与执行分离（信号出目标仓位，不直接出单） | 便于风控与复现；同一信号可换通道执行 | 策略只输出**目标权重矩阵**（`quant/strategy/base.py`），`multifactor` 也是 |
| 订单生成量化到整数手、按可用资金/可卖数量换算 | 避免废单、避免超卖 | `scripts/trade.py` 的 `target_orders()`：先卖后买、整手、卖出不超 `available` |
| **事前风控**（pre-trade risk check）：价格偏离、单票集中度、总仓、单笔金额、单日笔数、换手、涨跌停 | 废单/乌龙指/冲击成本都在这一层拦掉 | `quant/execution/guard.py` 的 `PreTradeGuard.check_batch()`，限额全在 `config.toml` 的 `[guard]` |
| 订单去重（幂等键、ClientOrderID） | 网络重试/误点导致重复下单是最常见事故 | `GatewayOrder.key`（`symbol\|side\|shares\|price`）+ `Ledger.record_order_keys()` + 护栏查 `submitted_keys` |
| 委托文件/消息留痕（订单 jsonl、回报文件） | 事后审计、复盘、纠纷举证 | `data/orders/<日期>-orders.preview.csv`、`-orders.csv`、`-orders.jsonl`（含 `submittedAt`）、`-fills.csv` |
| 交易前读账户（资金/持仓/可卖） | 不与柜台状态脱节 | `Ledger`（`quant/execution/ledger.py`）+ 通道 `query_account()` |
| T+1 与可用股数 | A 股当日买入不可卖 | `Ledger.apply_fill()` 买入不加 `available`；`settle()` 在新交易日解锁 |
| 日终对账（statement reconcile） | 账本与柜台必须一致，否则次日全错 | `Ledger.reconcile(statement)` + `python -m quant trade reconcile --statement 对账单.csv` |
| 急停开关（kill switch） | 出错时一键停止一切提交 | 存在 `data/KILL_SWITCH` 文件即拒绝所有提交（护栏第一道 + `trade confirm` 前置检查） |
| 上线前环境自检 | 数据源/时钟/通道/限额先验一遍 | `python -m quant doctor`（`quant/doctor.py`），产出 `results/doctor.json/.md` |
| 绩效与风险归因 | 判断策略是否失效 | `quant/backtest/metrics.py`（夏普/回撤/VaR/换手/暴露/Beta/Alpha/IR）+ `quant/report.py` |

## 3. 中国市场的合规要点（要点梳理，务必与券商核实）

监管框架（公开信息）：

- 证监会《证券市场程序化交易管理规定（试行）》（2024-05-15 发布）；
- 沪深北交易所《程序化交易管理实施细则》（2024-04-03 发布，**2025-07-07 起施行**），覆盖程序化交易**报告管理、交易行为管理、信息系统管理、高频交易管理、沪深股通管理、监督检查**等，并对**四类异常交易行为**重点监控（[\_证券时报\_报道](https://www.stcn.com/article/detail/1644893.html)、[\_人民网\_报道](http://finance.people.com.cn/n1/2025/0707/c1004-40516156.html)）。

对**你这个规模（≤50 万、日线低频）**的实际含义：

1. **手工下单（本文默认的半自动模式）不属于「程序化交易」申报范围**——订单在券商 App 里由你点击成交，券商看不到任何自动化报盘。这也是本工程默认 `csv` 通道的原因之一。
2. **一旦启用 QMT 自动下单（`[gateway] name="qmt"`），你就是「程序化交易投资者」**：需要按券商流程**报备账户与策略信息**、签署相关协议，并接受异常交易行为监控。具体是否要求、要填什么材料，**问你开户券商的客户经理或机构业务部**，不要凭本文操作。
3. **高频交易的认定与额外义务**（每秒/每日申报撤单笔数、报撤单频率、日内频繁回转等）针对的是高频策略；日线低频、每天几十笔的调仓**通常不触及**，但阈值以交易所规则原文与券商口径为准。
4. **异常交易行为**（瞬时申报速率异常、频繁瞬时撤单、频繁拉抬打压、长时间维持大量申报等）无论是否程序化都会被监控。本工程的护栏与此方向一致：单日笔数上限、单票集中度、换手上限、价格偏离上限、涨跌停不追/不砸，都在 `[guard]` 里。
5. **本工程不做的事**（刻意）：不接券商账号密码、不绕过券商风控、不做拆单规避监控、不做日内高频回转。

> 本文提到的法规信息来自公开报道，**可能滞后**；实盘前请以证监会/交易所原文和你券商的最新要求为准。

## 4. 半自动标准作业流程（SOP）

**盘前（交易日 9:00 前）**

```powershell
python -m quant doctor                 # 环境自检：数据源/时钟/通道/限额；有 fail 先别做
python -m quant trade plan             # 出建议单 + data/orders/<日期>-orders.preview.csv
```

人工核对建议单（这一步不能省）：金额与手数是否合理、是否停牌/退市/ST（`[guard] banned_symbols` 手填）、
是否有涨跌停、现金是否够、当日是否有特殊事件。

**盘中（9:30–11:30 / 13:00–15:00）**

```powershell
python -m quant trade confirm --yes    # 写入正式订单文件（dry_run=true 时只落文件；qmt 通道才是真报盘）
```

按 `data/orders/<日期>-orders.csv` 在券商客户端逐笔委托（限价，价格就是文件里的 `price`）。

**回报**

```powershell
python -m quant trade record --fills "600519.SH:100:1580.5:39.51;000001.SZ:-200:11.20:5.6"
# 或：把券商成交明细整理成 <日期>-fills.csv，用 --file 导入
python -m quant trade status             # 现金 / 市值 / 总权益 / 持仓 / 可卖 / 累计费用
```

**日终**

```powershell
python -m quant trade reconcile --statement 对账单.csv   # 差异会自动列出并返回非 0
```

**急停**：任何时候 `New-Item data\KILL_SWITCH`（或在资源管理器里新建这个空文件）→ 之后所有 `confirm` 与提交都被拒；
确认无误后删除该文件恢复。护栏第一道检查也是它。

## 5. 切到全自动（QMT）前必须做完的事

1. 券商侧：开通程序化交易权限（可能要资金门槛/临柜/协议），拿到 MiniQMT（迅投）客户端与资金账号；
2. 本机：安装并**常驻登录** MiniQMT；`pip install xtquant`（本工程不预装）；
3. `config.toml`：

```toml
[gateway]
name = "qmt"
dry_run = true                     # 先保持 true！qmt 通道在 dry-run 下只走本地预览
qmt_userdata = "C:/国金QMT交易端/userdata_mini"   # 你的实际路径
qmt_account = "你的资金账号"
qmt_account_type = "STOCK"
```

4. `python -m quant doctor --deep` → 检查项会 `tasklist` 查 `XtMiniQmt.exe` / `XtItClient.exe`；
5. **先用 dry-run 跑一遍**：`trade plan` + `trade confirm`，确认订单文件内容与预期一致；
6. 再把 `dry_run = false`，用**最小 100 股**试单，核对：委托号、成交回报口径、费用计算、`record` 后的持仓是否与客户端一致；
7. 全对之后再放到正常标的。**自动下单期间不要同时手工操作同一账户。**

`qmt` 通道的已知边界：只做了下单/撤单/查账户/查成交的最小封装，**真机未验证**（本机没有客户端）；
不同券商的 MiniQMT 版本接口字段可能略有差异，`quant/gateway/qmt_gateway.py` 的 `describe()` 会打印这条警告。

## 7. 已知限制（别把它们当 bug）

- **只做日线低频**：没有分钟/tick 数据，不做日内回转；信号日到成交日隔了一夜，跳空风险由你承担。
- **涨跌停是近似判定**（用昨收 × 涨跌幅 + ε），不判一字板能否成交；真实成交概率由券商撮合决定。
- **无排队/撮合模型**：回测按下一根 K 线开盘价成交，不考虑盘口深度（除 `max_volume_participation` 的粗略约束）。
- **ST/退市/停牌自动识别需人工维护** `banned_symbols`；`tradable` 只判「有没有价量」。
- **`push2 clist` 本机不可用**：全市场股票全集用新浪列表接口；取数脚本落地前请先看 doctor 报告。
- **不替代你的判断**：回测漂亮 ≠ 实盘赚钱；样本外、交易成本、滑点、容量都会吃掉收益。
